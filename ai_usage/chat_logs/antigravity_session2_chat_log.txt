SECTION 1 — QUERY CONCATENATION & NONSENSE INPUT DRIFT BUGS
================================================================================
Date: 2026-09-08

User prompt:
  "is there any search query that repeated the same sentence twice. For nonsense
   input, it also generated an empty query and kept searching, eventually returning
   an unrelated source...
   Two bugs found in evaluation results. First: search_agent.py's loop occasionally
   produces a query where the same phrase appears twice concatenated with no separator
   (e.g. 'Gloamreach established Year of the Black Dawn Age of Shadows recordGloamreach
   established Year of the Black Dawn...').
   Second: For nonsense input, it generated an empty query and kept searching."

Error Analysis:
  1. Concatenated Duplicate Queries:
     In `src/agent/query_rewriter.py`, regex parsing of model reasoning outputs used
     broad match patterns that captured repeated generated phrases or thought markers
     without word-boundary segmentation. Under greedy decoding (temperature=0.0),
     the LLM occasionally repeated partial phrases when reformulating queries, which
     was then passed uncleaned into the retrieval pipeline.
  2. Nonsense / Empty Query Drift:
     When given nonsense input (e.g. "asdfghjk..."), the query rewriter generated
     whitespace or an empty string. The search loop did not guard against empty
     query strings, passing an empty vector query to ChromaDB which retrieved
     arbitrary low-similarity chunks and led to hallucinated/unrelated sources.

Fixes & Verification:
  - In `src/agent/query_rewriter.py`: Added regex token sanitization and algorithmic
    phrase deduplication, stripping repeated consecutive n-grams and trailing quotes.
  - In `src/agent/search_agent.py`: Added defensive drift guards:
    * If a reformulated query is empty, whitespace, or identical to the previous
      round's query, immediately terminate the loop and declare insufficient evidence.
  - Verification:
    Created unit test script `scratch/test_dedup_guards.py`. Tested repeated queries
    and nonsense inputs; verified that repeated phrases are cleanly deduplicated and
    nonsense inputs stop immediately after exhaustion without drifting into false matches.

SECTION 3 — INFRASTRUCTURE FRAGILITY: VOYAGE AI RATE LIMITS & RERANKER FALLBACK
================================================================================
Date: 2026-09-09

User prompt:
  "check if i have indexed the corpus and if not do the changes...
   Log this whole incident. This is genuinely good material for docs/limitations.md —
   a real, documented example of infrastructure fragility (rate limiting,
   incomplete indexing) that your team caught before the demo, not during it:
   ## Known issue: Voyage AI rate limiting without billing"

Error Encountered:
  During local corpus indexing and test queries on a standard Voyage AI tier:
  `voyageai.error.RateLimitError: 429 - 10,000 TPM limit exceeded`
  Large document batches and rapid back-to-back queries hit the free tier quota,
  halting the indexing process and risking agent execution failure.

Actions Taken:
  1. Resilience in Retrieval (`src/retrieval/reranker.py`):
     Wrapped Voyage reranker API calls in a try-except block catching `RateLimitError`
     and HTTP 429 errors. When rate-limited, the system logs a warning and
     gracefully falls back to raw ChromaDB vector store similarity rankings,
     ensuring the search agent never crashes during user interaction.
  2. Documented in `docs/limitations.md`:
     Added empirical documentation of the 10k TPM Voyage rate limit incident,
     mitigation steps (lowering batch size to 4, adding reranker fallback), and
     recommendations for competition deployment.

SECTION 4 — MODEL COMPARISON EXPERIMENT: gpt-oss-20b VS gpt-oss-120b
================================================================================
Date: 2026-09-09

User prompt:
  "Model/prompt experimentation (still on the original list, never done):
   compare gpt-oss-20b vs 120b on the evidence-checker, document in docs/experiments.md."

Experimental Setup:
  - Built evaluation script `scratch/compare_models_evidence_checker.py`.
  - Tested 6 representative Track 1C scenarios: multi-hop partial evidence,
    multi-hop complete evidence, source authority conflict (Codex vs Wiki),
    unanswerable distractor, partial single-hop gap, and equal-authority conflict.
  - Temperature: 0.0 (greedy decoding).

Findings & Decision (Logged as Experiment 007 in `docs/experiments.md`):
  - Accuracy: Both models scored 6/6 (100%) on status classification (sufficient vs insufficient).
  - Schema: Both models produced 100% valid JSON without parsing errors.
  - Latency: `gpt-oss-20b` was ~30% faster (0.58s vs 0.83s).
  - Qualitative Reasoning:
    * `gpt-oss-120b` explicitly followed authority weighting rules in reasoning,
      noting: "The codex provides an exact founding year (246 AS) and is the
      authoritative source, overriding the contested popular accounts."
      `gpt-oss-20b` merely cited the date without explaining the override.
    * `gpt-oss-120b` produced higher-specificity descriptions in `missing_information`
      preserving relational bridge entities for the query rewriter.
  - Decision: Kept `openai/gpt-oss-120b` as the production reasoning model for Track 1C.

SECTION 5 — FULL-ARCHIVE VECTOR DB INTEGRATION & GROQ 8k TPM TUNING
================================================================================
Date: 2026-09-09

User prompt:
  "I have the data/vector_db zip file... What’s the next step"

Actions & Resolutions:
  1. Archive Extraction & Verification:
     - Extracted `data/vector_db.zip` (52 MB, 8 files) to `data/vector_db/`.
     - Verified with `check_index_status.py`: exactly 2,186 chunks indexed across
       chronicles, codex, wiki, and ephemera.
  2. Live Retrieval Integration:
     - Switched `src/agent/search_agent.py` to import `from src.retrieval.search import search`.
  3. Groq HTTP 413 Rate Limit Incident & Fix:
     - Error: Initial live execution failed with:
       `HTTP 413: Request too large for model openai/gpt-oss-120b in organization ... Limit 8,000 TPM`.
     - Root Cause: Default `SEARCH_TOP_K=15` retrieved 15 full text chunks (~8,642 tokens),
       exceeding Groq's on-demand per-minute token ceiling.
     - Solution: Tuned `SEARCH_TOP_K` from 15 to 5 across `search_agent.py`, `.env.example`,
       and `src/app.py`.
     - Result: Token payload per round dropped to ~2,500 tokens, well below the 8,000 TPM
       ceiling. Vector retrieval recall remained 100% across the benchmark suite.
     - Documented as **Decision 006** in `docs/decisions.md`.
